## Abstract

Abstract The widespread adoption of large language models (LLMs) has made
GPU-accelerated inference a critical part of modern computing infrastructure.
Production inference systems rely on CUDA kernels
to implement core transformer operations,
yet these kernels are highly susceptible to memory-safety bugs due to
model-dependent tensor layouts, intricate memory indexing,
and massive thread-level parallelism.
Such bugs can corrupt model weights, crash inference services,
or even enable adversarial attacks.
Existing techniques either depend on unavailable hardware,
incur high overhead, or fail to handle kernel inputs with variable lengths,
and none can effectively detect CUDA memory bugs in
LLM inference systems. This paper presents Model2Kernel, the first practical system for automatically verifying the memory safety
of CUDA kernels used in LLM inference.
Model2Kernel performs model-aware dynamic analysis to determine how each model invokes kernels and to classify kernel
arguments as either fixed by the model
architecture or controlled by model users.
Using this information,
Model2Kernel then applies CUDA-specialized symbolic execution, supported by new abstractions for dynamic tensor memory and thread identifiers, to accurately pinpoint memory bugs in kernels.
In the evaluation on CUDA kernels and models from vLLM, Hugging Face, and recent LLM research papers,
Model2Kernel discovers 353 previously unknown
bugs while producing only nine false positives, demonstrating its effectiveness.

## 1 Introduction

The rapid adoption of large language models (LLMs) has driven
an explosion of inference workloads across chat bots [2, 1, 22], search [44, 91],
recommendation [80, 86, 5],
copilots [15, 90, 40], scientific computing [77, 45, 7],
and countless other areas [84, 8, 10].
These services now operate at large scale and serve real users,
making LLM inference systems a critical part of modern computing infrastructure.

LLM inference systems rely on a layered software architecture. Model developers publish Python model files and weights—such as those
released on Hugging Face [29]—which inference frameworks (e.g., vLLM [42], SGLang [87],
Transformers [30]) load and execute. These frameworks manage inference requests and register GPU kernels to link Python-level
logic with host-side wrapper code. The wrapper code prepares CUDA
kernel inputs and configures kernel launches. At the lowest layer, CUDA kernels perform the core linear algebra
operations required by transformer architectures on the GPU. This
design supports rapid innovation but substantially increases system complexity.

Memory-safety bugs remain a persistent challenge [72],
and CUDA kernels are particularly vulnerable for three main reasons.
First, fine-grained index calculations across large tensors and thousands of threads make kernels prone to out-of-bounds accesses and data races.
Second, as model architectures grow larger [84] and inference sequences become longer [74, 23], the risk of integer overflows in CUDA kernels increases.
Third, the complexity of the entire inference stack can produce tensor layouts that violate kernel assumptions [16, 52], further increasing the potential for memory-safety errors.

Memory-safety bugs in CUDA kernels can lead to severe consequences.
Out-of-bounds accesses and data races often trigger “illegal memory access”
errors on the GPU, potentially crashing the entire inference service [63].
Recent work has also shown that such vulnerabilities can be exploited to modify arbitrary GPU memory or even achieve arbitrary code execution [34, 26, 57].
Because inference systems interact with external users and may receive attacker-controlled inputs, exploitable memory
bugs in kernels pose a serious security risk,
potentially allowing adversaries to alter deployed model weights or
compromise the entire system.

Existing techniques for detecting memory bugs
in CUDA kernels fall into two main categories.
Dynamic methods
track metadata for GPU memory buffers and
check whether pointer values fall within valid bounds before dereferencing [73, 43, 59, 60, 43, 92, 82, 28, 88, 89, 49].
However, these methods either incur
high runtime overhead or rely on
extra hardware not yet widely available.
Static tools, on the other hand, cannot handle buffers with sizes determined at runtime or the variability of kernel launch configurations [6, 46, 48, 35, 47, 65, 50, 54].
As a result, no existing technique offers comprehensive and practical memory bug detection
for the CUDA kernels in modern LLM inference systems.

We argue that symbolic execution provides a promising approach for detecting memory-safety issues in CUDA kernels.
Many critical vulnerabilities (e.g., integer overflows, buffer overflows, data races)
can be formulated as constraint-satisfaction problems over indices,
tensor shapes, and thread identifiers,
a domain where symbolic execution excels.
In addition, CUDA kernels are generally simpler than typical C/C++
programs: they primarily operate over multidimensional tensors,
use few custom data structures, and rarely involve complex pointer
operations (e.g., pointers to pointers) or indirect function calls.
These characteristics make CUDA kernels easy for symbolic analysis.

However, applying symbolic execution to CUDA kernels
presents several challenges. First, existing symbolic execution techniques
have difficulty handling dynamic arrays, yet most CUDA kernels in LLM systems
operate on tensors whose shapes are often determined
only at runtime. Second, CUDA kernels execute across thousands of parallel
threads, and scaling symbolic execution to these threads is non-trivial.
Third, kernel behavior may vary across different model architectures, and automatically inferring these architectures and understanding how they affect kernel execution remain complex due to the intricacies of the full inference stack.

To address these challenges, we design Model2Kernel,
a fully automated analysis framework that verifies whether CUDA kernels exhibit memory-safety issues when used together with a given LLM model.
Model2Kernel targets four types of bugs in CUDA kernels:
buffer overflows, integer overflows,
data races, and NULL pointer dereferences, and supports models sharing the same format as those released on Hugging Face.
As shown by Figure [1](#S1.F1), Model2Kernel consists of two major components: cuKLEE and HFProbe.

cuKLEE is a symbolic execution engine specialized for CUDA kernels.
To handle input tensors whose memory layouts are determined at runtime,
we model each tensor as a distinct and widely separated memory region.
This abstraction simplifies pointer–tensor association and
makes bounds checking more tractable.
We then introduce symbolic variables to represent each tensor’s base address,
element count, dimensions, and other properties. With these variables,
cuKLEE can handle more than 100 tensor methods by adding the appropriate constraints to its execution states.
We also model CUDA thread identifiers as symbolic variables,
enabling unified symbolic execution that captures both thread-shared and thread-specific computations in a single pass.
This design allows cuKLEE to scale to thousands of CUDA threads.

Figure: (a) The Python model code of DeepseekV3ForCausalLM.

HFProbe “executes” each model without requiring GPU hardware. It profiles how the model invokes CUDA kernels and automatically
identifies which kernel inputs are determined by the model architecture
(and therefore should remain fixed during cuKLEE’s analysis)
and which inputs are controlled by end users
(and should be treated as variable). Incorporating this
information
allows cuKLEE to analyze kernels more efficiently and accurately.
In addition, HFProbe statically identifies all CUDA kernels that may be invoked by a given model and automatically mutates the model’s
configurations to trigger more kernels, ensuring more comprehensive analysis of both the model and its CUDA kernels.

We evaluate Model2Kernel on CUDA kernels and models from three sources: all text-generation models in vLLM [42] and the related kernels,
all Hugging Face models with custom kernels,
and models and kernels from four recent research publications [81, 55, 64, 39].
In total, Model2Kernel identifies 353 memory bugs, including 328 integer overflows and 25 out-of-bounds accesses, with only nine false positives, demonstrating
its effectiveness in detecting memory safety issues for CUDA kernels.
We further compare Model2Kernel with Honeycomb [54],
GKLEE [47], and
ESBMC-GPU [65] on 20 known vLLM CUDA kernel bugs.
Model2Kernel successfully detects 15 of these bugs, far more than the baseline techniques, highlighting its good bug coverage and
clear improvement over existing techniques.
An ablation study shows that both HFProbe and cuKLEE are critical for Model2Kernel
to achieve this level of effectiveness.

In sum, we make the following contributions:

- •
We design cuKLEE, a CUDA-specific symbolic execution engine that supports tensors with dynamic shapes and scales to thousands of CUDA threads.
- •
We develop HFProbe, a dynamic model profiler that analyzes how models invoke CUDA kernels and infers model-dependent kernel arguments.
- •
By integrating cuKLEE with HFProbe, we build Model2Kernel, a fully automated framework for detecting CUDA memory bugs in LLM inference systems, and we demonstrate its effectiveness through comprehensive experiments.

### 2.1 Hugging Face Models

Hugging Face is the largest platform for
sharing pre-trained models [29],
offering both a model marketplace and libraries that facilitate model integration
into LLM inference frameworks (e.g., vLLM [42], SGLang [87], Transformers [30]). Today, it hosts millions of models, including major open-source foundation models (e.g., Qwen, LLaMA) and their variants, making it a central hub for the AI community.

A model released on Hugging Face typically contains
four types of files.
The config.json file defines the
model’s architecture, including layers,
hidden size, activation functions,
and other structural parameters.
The model-weight files store the trained parameters.
The Python code files define classes that extend nn.Module
and implement the model’s architecture.
One top-level class assembles all model components together,
with its forward() method
as the entrance of the model’s whole forward pass.
For example, Figure [2](#S1.F2) shows simplified model code for DeepseekV3ForCausalLM, and forward() in line 4 begins the model’s inference process.
Finally, documentation files (e.g., README.md) provide instructions, usage examples,
and licensing information.

### 2.2 The CUDA Programming Language

CUDA is the dominant general-purpose programming language
for exploiting GPU computational power [21],
and most GPU kernels in inference systems are written in CUDA.

CUDA source files (.cu files) typically contain two types
of code: host wrapper functions and GPU kernel functions.
Host wrappers run on the CPU and are exposed to
Python code in inference systems via registration or binding macros [36, 67] (e.g., Figure [2](#S1.F2)).
They process input Tensors
from Python code into kernel arguments, configure launch parameters (e.g., number of thread blocks,
threads per block, shared-memory size),
and call the kernels.
CUDA kernels run on the GPU. They define the computation performed
by each parallel thread. Under CUDA’s execution model,
a kernel runs across many threads organized into blocks and grids.
Each thread uses built-in identifiers (e.g., blockIdx.x, threadIdx.x)
to determine its location in this hierarchy and
the portion of input data it processes.

Function fused_add_rms_norm() in Figure [2](#S1.F2) is a wrapper function.
It computes the model’s hidden size and the number of input tokens in lines 2–3, sets the number of blocks to the token count (line 4) and threads per block to 256 (line 5),
and then launches kernel function fused_add_rms_norm_kernel() with pointers to the underlying memory of the input tensors,
the epsilon parameter, and the computed hidden size and token number in lines 8–9.

Figure [2](#S1.F2) shows the launched CUDA kernel.
It fuses element-wise addition, RMS normalization, and scaling by weight.
To improve performance, the kernel uses vectorization.
It calculates how many
vector units fit into the hidden size in line 10, allocates
a shared-memory variable that all threads in the block can access in line 11, and
casts the input pointers to vectorized types in lines 14–16.
The loop in lines 18–25 distributes work across threads. Each thread determines which part of data it should process based on
the block’s starting offset (blockIdx.x * vec_hidden_size), its thread ID (threadIdx.x), and additional loop increments
equal to the block size (blockDim.x).
In each iteration, a thread loads a vector in line 21, adds residuals in line 22, and accumulates the squared sum into the thread-local variance in line 23.
Next, a block-wise reduction sums variances from all threads in lines 27–29.
The kernel computes the RMS normalization coefficient
and stores it to the shared memory in line 31.
Finally, the second loop in lines 36–43 uses the same indexing pattern to apply the normalization, multiplies by weight, and writes the results back to input.

### 2.3 Memory Safety Issues in CUDA Kernels

Unfortunately, CUDA kernels in LLM inference systems are prone to memory bugs (e.g., integer and buffer overflows). This arises partly because kernels must
implement complex, highly optimized matrix
operations to exploit hardware features such as
caches and vectorized instructions (e.g., line 21 in Figure [2](#S1.F2)),
increasing the likelihood of programming errors.
Moreover, inference systems integrate kernels and models from different groups, so a kernel correct for one model may fail for another.
For example,
the model’s hidden size of 8192 in Figure [2](#S1.F2)
and line 8 of Figure [2](#S1.F2) yield width = 8 and vec_hidden_size = 1024 in Figure [2](#S1.F2).
The kernel launches one block per token, so blockIdx.x equals the number of tokens or the batch size multiplied by the sequence length.
With batch size up to 64 and sequence length up to 128,000, the product blockIdx.x * vec_hidden_size in line 20 can easily exceed the int32 limit,
triggering an integer overflow.
The overflowed value is then used as an index into input_v, causing a buffer overflow.

We conduct an empirical study to assess the prevalence and characteristics of CUDA memory bugs in LLM inference systems. By examining vLLM’s change logs, we identify 20 resolved memory bugs in CUDA kernels, including ten integer overflows (also causing buffer overflows), eight additional buffer overflows and two null-pointer dereferences. 17 occur on input tensors residing on GPU global memory, while three happen on GPU shared memory.
13 were reported by users during production, six detected by unit tests,
and one found via code review. These results highlight the prevalence of CUDA memory errors in LLM inference systems
and their strong association with tensors.

CUDA memory errors can easily lead to incorrect computations in LLM inference systems.
Moreover, GPUs trigger an “invalid memory access” when unallocated memory is accessed, which can crash the entire inference system, as observed in our study [13].
Compounding the risk, recent research shows that such memory errors can be exploited for attacks, including arbitrary memory writes and code execution on GPU [34, 26, 57], highlighting the urgent need to address CUDA memory bugs in LLM inference systems.

### 2.4 Symbolic Execution Techniques

Symbolic execution [79] is a static analysis
technique that “executes” programs with symbolic,
rather than concrete, inputs.
By systematically exploring execution paths and invoking constraint solvers
to assess path feasibility, it can generate inputs that expose potential defects.
Numerous symbolic execution techniques have been developed. They have successfully detected diverse issues (e.g., buffer overflows, integer overflows) in critical software systems [12, 76, 17, 33, 9, 78].

Existing symbolic execution techniques struggle
with dynamic arrays whose sizes are only known at runtime.
Consider how KLEE [12] handles the allocation “buffer = (int *)malloc(n * sizeof(int))”
where n is fully user-controlled and marked symbolic.
KLEE forks three states upon encountering this statement. The first assumes $n=1$,
typically producing false positives for later accesses because real inputs are usually much larger.
The second assumes $n>2^{31}$, causing KLEE to report
“null page access” once buffer is used.
The third treats $n$ as a symbolic uint32,
issues a “concretized symbolic size” warning, and terminates the exploration for the state.
KLEE and most symbolic executors handle dynamic arrays in this simplified way because they use a contiguous memory model.
If an array’s size is symbolic, the addresses of all subsequent buffers also become symbolic,
dramatically complicating memory–access reasoning for those buffers.

This limitation is particularly problematic for CUDA kernels,
especially those used in LLM inference, because they operate directly on tensor memory whose shapes depend on model
architectures or even on user-provided token counts (e.g., the dimensions of the input tensor in Figure [2](#S1.F2)).
Consequently, although prior efforts have explored symbolic execution for CUDA kernels [6, 46, 48, 35], none can be effectively applied to CUDA code in modern LLM inference systems.

## 3 Overview of Model2Kernel

Model2Kernel is designed to detect memory bugs in CUDA
kernels for LLM inference systems. As shown in Figure [1](#S1.F1), it consists of two
components: HFProbe, which collects model-architecture information, and cuKLEE, which
identifies CUDA memory bugs using this information.

HFProbe supports two backends, vLLM [42]
and Transformers [30],
enabling it to analyze
any model compatible with these frameworks, including all models from Hugging Face [29].
For each CUDA kernel,
HFProbe determines which kernel
inputs are model-dependent and which are user-controlled. For example, when analyzing the model in Figure [2](#S1.F2),
HFProbe infers that the last dimensions of tensors input, residual, and weight in Figure [2](#S1.F2) are all 7168, the model’s hidden size,
while the first dimensions of input and residual correspond to the number of input tokens.

cuKLEE is a symbolic execution engine specialized for CUDA
that detects out-of-bounds accesses, integer overflows, data races, and null-pointer dereferences.
Using model information provided by HFProbe,
it identifies buggy lines in CUDA kernels and generates concrete values for user-controlled kernel inputs that can trigger the bugs.
For example, for Figure [2](#S1.F2),
it reports that when the first dimension of input is 2,432,000 (batch size 19, sequence length 128,000),
line 20 experiences an integer overflow and line 21 performs an out-of-bounds access in Figure [2](#S1.F2).

Model2Kernel enhances the safety and reliability of inference systems in two ways. First, model developers can use it to verify existing
CUDA kernels correctly support newly developed model architectures and expected input token counts.
Second, CUDA developers can use it to ensure that new kernel optimizations do not introduce memory bugs and remain compatible with models already deployed in production.

## 4 Design of Model2Kernel

This section gives the detailed design of Model2Kernel.

### 4.1 cuKLEE: Symbolic Execution on CUDA

cuKLEE begins its analysis at each wrapper function (e.g., Figure [2](#S1.F2)) to gather information about
how the CUDA kernel (e.g., Figure [2](#S1.F2)) is invoked.
It then examines the kernel to detect potential memory bugs.
cuKLEE allows users to specify constraints on the wrapper’s inputs,
so that information about model architectures can be incorporated
to improve both accuracy and performance.
In summary, we address three key challenges in building cuKLEE.

First, as discussed in Section [2.4](#S2.SS4), existing symbolic execution techniques have difficulty handling dynamic arrays.
In contrast, most CUDA kernels in LLM inference systems operate on the raw memory of tensor objects (e.g., input in line 4 of Figure [2](#S1.F2)), whose shapes vary depending on model architectures or user-provided tokens.
How can cuKLEE analyze memory operations on tensors with dynamic shapes?

Second, wrapper functions often call tensor
methods to set up parameters for kernel launches.
These methods involve complex memory management, and analyzing
them in full would significantly increase execution time and reduce precision.
How can we summarize these tensor methods to make cuKLEE both efficient and accurate?

Third, CUDA kernels run across many threads,
and analyzing each thread separately would result in redundant work.
How can we share symbolic execution results across threads to avoid unnecessary computations?

#### 4.1.1 Memory Model of cuKLEE

Tensor Memory.
GPUs have three types of memory: global, shared, and local.
All input tensors and tensors created by wrapper functions reside
in global memory and are accessible to all GPU threads.
We model the memory regions of these tensors as discrete and
well-separated, because all input tensors
are allocated by the inference system, which
prevents CUDA kernel programmers from making any assumptions
about their layout. Consequently, in CUDA kernels,
a pointer to an element of one tensor never refers to an element
of another tensor through arithmetic computations.

As shown in Table [1](#S4.T1),
we associate each tensor with a set of symbolic constraint variables.
cuKLEE uses these variables to construct constraints when
it analyzes specific instructions or tensor methods.
Note that the number of dimensions ($D$)
may remain unknown even at the end of analysis. Therefore, we maintain a map to record all known dimensions,
where the keys are dimension indices and the values are the corresponding symbolic variables (e.g., $d_{1}$, $d_{2}$).
For example, line 2 of Figure [2](#S1.F2) accesses the last dimension of tensor input by calling input.size(-1).
cuKLEE processes this line by adding an entry to the map with key $-1$ and value $d_{D-1}$, and it also
adds a constraint representing hidden_size is equal to $d_{D-1}$
into its execution state.

This modeling strategy greatly simplifies
the detection of out-of-bounds accesses on tensor memory.
For each tensor,
all pointers to its elements carry value constraints
that relate them to the tensor’s base address.
Using this information, cuKLEE can
quickly identify the corresponding tensor
and retrieve its associated metadata.
When a pointer is dereferenced,
cuKLEE can construct constraints indicating
the pointer is outside the tensor’s valid memory region and invoke a constraint solver to validate the feasibility.
For example, when analyzing line 21 in Figure [2](#S1.F2), cuKLEE
immediately determines that the memory access must be
checked against the bounds of input.
This follows the constraint established in line 14, which binds input_v to the base address of input.
In contrast, without such modeling, a symbolic execution engine (e.g., KLEE)
must scan all allocated memory
objects to infer which
object a pointer may reference
before performing any boundary check.

Other Memory.
For global and local memory allocated within wrapper and
kernel functions, we adopt the contiguous memory model
used by KLEE.
CUDA shared memory can be allocated dynamically at kernel launch, where cuKLEE infers a concrete or symbolic size from the launch parameters, or statically with a fixed size in the kernel (e.g., line 11 of Figure [2](#S1.F2)), in which case the size
is known directly. cuKLEE also treats global, shared, and
local memory as separate regions and resolves pointer targets only within the region to which they belong.

#### 4.1.2 Handling Tensor Methods

We group the 140 Tensor and TensorIterator methods
into four categories and handle each category differently in cuKLEE.
Table [2](#S4.T2) provides representative examples.

First, 36 methods return tensor properties.
For example, input.numel() in
line 3 of Figure [2](#S1.F2)
returns the number of elements in input.
For these methods, cuKLEE models their return
values using the constraint variables defined in Table [1](#S4.T1).

Second, 70 methods create a new tensor or produce a
sub-tensor of an existing one.
For such methods, cuKLEE creates a
new set of constraint variables for the resulting tensor and
adds constraints that relate them to the original tensor
based on the method’s semantics. For example, Table [2](#S4.T2) shows the constraints for B = A.sum(0). Since
A.sum(0) reduces A along its first dimension, B has one fewer dimension than A, and its
$i$-th dimension equals to the $(i+1)$-th
dimension of A.

Third, four methods inspect properties of a tensor. For these, cuKLEE adds constraints that encode the conditions
required for the check to succeed.

Fourth, 30 methods do not affect cuKLEE’s analysis.
These methods are therefore ignored.

#### 4.1.3 Handling CUDA Threads

CUDA organizes threads into blocks and blocks into grids. Although all threads execute the same kernel code,
their behavior differs based on their thread and block identifiers,
which programmers also use to partition input data.
cuKLEE follows this execution model
by treating thread and block identifiers as symbolic variables rather than enumerating all possible values, allowing a single symbolic execution to represent the behavior of all threads. Thread-independent bugs are handled as in sequential programs, while thread-dependent bugs (e.g., line 20 in Figure [2](#S1.F2)) are captured
through constraints over these symbolic identifiers.
cuKLEE then checks the feasibility of these conditions under the kernel’s launch configuration.

To support this analysis,
we introduce two classes of constraint variables:
six ID variables and six launching variables, as shown in Table [3](#S4.T3).
ID variables
are constrained by launching variables
according to CUDA semantics (e.g., blockIdx.x < gridDim.x).
Constraints on launching variables are
obtained when analyzing the kernel launch (e.g., blockDim.x=num_tokens in Figure [2](#S1.F2)).

For loops that distribute work across threads
(e.g., the highlighted loops in Figure [2](#S1.F2)),
cuKLEE analyzes the loop body only once rather than forking execution at each termination check.
cuKLEE adds the loop’s exit condition (e.g., idx >= vec_hidden_size) for the remaining execution.
The loops’ termination conditions are usually simple to ensure correctness for thousands of threads, making single-pass analysis enough.
cuKLEE also detects data races within such loops by creating a second set of ID variables that represent a different thread with the same launch constraints.
cuKLEE adds constraints indicating the two threads are different by negating
the constraints that the two threads’ six ID variables are equal pairwise.
For each global memory access, cuKLEE checks whether this second thread may perform a conflicting write to the same address. A similar check is performed for shared memory,
excluding constraints on blockIdx.x/y/z, since only threads in the same block can access shared memory.

#### 4.1.4 Additional Considerations

Initial Constraints.
Before analyzing each wrapper function, cuKLEE introduces three constraint
variables: $BS$ for batch size, $SL$ for sequence length, and $TC$ for the total
number of tokens, with the relation $TC=BS\times SL$. In addition to the
constraints provided by HFProbe, we further restrict $BS\leq 1000$ and $SL\leq 1{,}000{,}000$. Many recent models already support context lengths of one
million tokens [18, 19], and maximum context lengths have increased by roughly a factor of 30 per year since 2023 [32].
These bounds therefore reflect
both current and near-future LLM capabilities.

Buggy Constraints.
cuKLEE detects four types of bugs.
Data-race detection is described in Section [4.1.3](#S4.SS1.SSS3); here, we focus on the other three.
To detect out-of-bounds accesses, cuKLEE adds constraints for each memory access via a pointer
indicating that the pointer is either smaller than the base address or larger than the upper bound of the buffer.
For integer overflows, it adds a constraint for each addition or multiplication
on 32-bit integers specifying the result exceeds the type’s maximum value. For null-pointer dereferences, cuKLEE adds constraints for each pointer dereference
indicating the pointer may have been computed from an unknown base pointer. We
assume that all input tensors are valid and that their base addresses are properly initialized.

Library and Instruction Support.
We leverage API summarization [38, 53]
to handle 91 CUDA APIs (e.g., cudaMalloc()) and
39 C/C++ library functions (e.g., methods of std::vector) that are commonly used by wrapper functions.
In essence, we use summarization to update the execution
state without performing inter-procedural analysis to explore their internal logic.
Similarly, we support 44 LLVM intrinsics and 59 inline assembly calls used in CUDA kernels.
For example, when processing llvm.nvvm.read.ptx.sreg.tid.x(), cuKLEE returns the symbolic variable representing threadIdx.x.

### 4.2 HFProbe: Dynamic Profiling of HF Models

HFProbe provides analysis contexts for CUDA kernels by supplying
concrete shapes for some (but not all) input tensors and placing constraints on their values. This reduces the number of symbolic variables
handled by cuKLEE, improving scalability and
decreasing false positives arising from unrealistic inputs.
As illustrated in Figure [1](#S1.F1), HFProbe operates in four stages.
It first performs static analysis to identify all CUDA kernels each input model may call.
It then executes the model with a real configuration using mocked CUDA kernels and records how the kernels are actually invoked.
Next, it mutates the configuration to exercise additional kernels
identified statically but not triggered dynamically.
Finally, it aggregates the collected information in a post-mortem analysis
to derive analysis contexts for cuKLEE.

#### 4.2.1 Static Call Graph Computation

Given a model’s Python implementation
(e.g., Figure [2](#S1.F2)),
we build a static call graph using the model’s forward()
method as the root.
The analysis is path- and field-sensitive and leverages
common coding patterns of Hugging Face models.
For example, we assume that a model object has no aliases
within its own implementation. Our analysis
identifies
all CUDA kernels used by the model.
However, the resulting call graph may also
include spurious kernels that are not actually used.
Existing Python call-graph analysis techniques cannot precisely
analyze Hugging Face models [37, 83, 70].
For instance, PyCG does not handle __call__,
preventing it from resolving calls to an nn.Module object—a common practice for invoking a layer’s forward()
method (e.g., line 5 in Figure [2](#S1.F2)).

Our analysis operates on the Abstract Syntax Tree (AST) of the input Python program.
It maintains an execution context where each program object is represented as an instance. The analysis creates the instance when analyzing the object’s class constructor.
Each instance stores its fields and their values in a dictionary.
The analysis processes each instruction with respect to this context and also updates
it according to the instruction’s semantics.

Our analysis begins with the model’s __init__() method
to initialize the context.
It then analyzes the forward() method to construct the call graph.
For each object field assignment
(e.g., line 3 in Figure [2](#S1.F2)),
the analysis updates the left-hand instance’s dictionary
using either the concrete value or the instance
referenced on the right-hand side.
For each function call, it performs interprocedural analysis: it maps the instances of actual arguments to the formal parameters of the callee.
If the receiver’s type is known only at the base class level,
all methods of possible derived classes are treated as potential callees.
At each branch, the analysis inspects the context to decide which path is feasible.
If both paths may occur, it clones the context and analyzes each path independently.
When encountering Python bindings to CUDA kernels (e.g., line 20 in Figure [2](#S1.F2)),
it records that the model calls the corresponding CUDA kernels.
All Python bindings and their links to CUDA kernels (e.g., Figure [2](#S1.F2)) are identified in a separate analysis using regular expressions.

#### 4.2.2 Profiling Backends

We modify the vLLM and Transformers inference frameworks
to serve as HFProbe’s backends and
to record runtime information during model inference.
To accelerate profiling, we disable all actual GPU computations,
allowing the modified frameworks to exercise models without GPU hardware.
Overall, three categories of
framework functions are changed.

First, for every CUDA kernel registered in the frameworks,
we replace calls to its Python binding with calls to a fake function.
As shown in Figure [3](#S4.F3.fig1), the fake function records
the call stack and the type of all input parameters.
For tensor inputs (e.g., input), it further
records their shapes and data types.
For primitive-type parameters, it records their concrete values.
If the original binding returns a tensor,
the fake function returns a zero-filled tensor
with matching shape and data type.
When an input tensor of an integer
data type contains nonzero values,
the fake function records its maximum and minimum values.
This helps capture potential index ranges used inside CUDA kernels,
which are useful for generating constraints
in execution contexts.

Second, we modify the model-loading functions so they only create tensors
with the correct shapes,
without actually loading any model weights.

Figure: Figure 3: The fake function for fused_add_rms_norm().

Third, although no GPU computations are executed,
we make sure the frameworks still follow the same control flow
they would use if GPU computations were running.
For example, without a real GPU, the module vllm._C
cannot be imported, which causes a runtime error.
We import a
fake module to address this issue.
As another example, for every tensor we create,
we adjust its internal properties so the frameworks believe the tensor’s
data is stored on the GPU.

Fourth, we optimize vLLM’s KV-cache management to initialize tensors
with minimal memory
and expand them using the expand() method to the correct shapes,
without more memory allocation.
Extra memory is only allocated for a tensor when it receives writes
beyond its initially allocated space.
This lazy allocation strategy eliminates pre-allocated memory
and reduces memory pressure for large models.

#### 4.2.3 Model Configuration Mutation

For each input model,
we adjust its execution configuration to trigger more CUDA kernels.
There are two types of configurations we modify: those defined in the model’s config.json file, and those defined by inference frameworks.

Several config.json parameters govern which CUDA kernels are used
during a model’s forward pass. For example, for the model in Figure [2](#S1.F2),
modifying quantization_config changes the quantization kernels, while reducing n_routed_experts from 256 to 128 alters the padding kernel used for token routing, switching from sgl_moe_align_block_size
to moe_align_block_size.

Because parameter names vary across models,
we use an LLM to generate modified config.json files. Leveraging its understanding of natural language and code, the LLM can produce
compatible configurations that activate targeted kernels.
For each CUDA kernel identified by static analysis but not triggered in prior runs,
we provide the model’s Hugging Face repository URL and the kernel name, and ask the LLM to produce a new config.json to trigger the kernel.
We run the LLM in agent mode so it
can inspect the repository, reference the example config.json,
and read the model implementation code.
However, not all generated config.json files are valid. For example, the model in Figure [2](#S1.F2) requires the activation function silu, and changing the hidden_act field in config.json will cause an assertion error.
We simply discard any modified config.json
that results in a runtime failure.

For framework-defined configurations, we consider both environment
variables and framework startup parameters.
We construct a mapping from each CUDA kernel to the configuration
required to activate it.
Building the mapping is a one-time effort, as it is framework-specific and applies
across all models. When a kernel needs to be triggered, we retrieve and apply its corresponding configuration.
If a kernel requires coordinated changes to both framework settings and config.json, we inform the LLM that the necessary framework configuration
has already been applied before requesting it to modify config.json.

#### 4.2.4 Context Generation

Given a configuration, we execute the model with varying batch sizes
and sequence lengths,
which together determine the number of input tokens.
For each kernel, we analyze the recorded values of tensor dimensions, primitive parameter values, and the minimum and maximum values of integer-valued tensors. From this data, we infer four categories of constraints
that together form the analysis context of cuKLEE:
1) strict linear relationships with batch size, sequence length, or token count;
2) invariant values determined by the model architecture;
3) equality relationships between the values; and
4) residual parameters that do not fall into the above categories
but may still exhibit indirect dependence on the model architecture;
for these, we impose an upper-bound constraint using the maximum value observed.

For example, after executing the model in Figure [2](#S1.F2)
with a configuration [31],
we infer that the last dimensions of input,
residual, and weight
in Figure [2](#S1.F2) are all 7168,
fixed by the model architecture,
that the first dimensions of input and residual
are token count, and that epsilon equals $1e-6$.

## 5 Evaluation

Implementation.
cuKLEE is built on KLEE v3.1 and operates on LLVM IR generated from CUDA source code.
We implement 31,002 lines of C++ to support
tensor abstractions, enable symbolic execution across CUDA threads,
and handle CUDA-specific instructions.
cuKLEE uses Z3 [24] as its constraint solver.
HFProbe is implemented in Python and performs call-graph analysis using the built-in AST module [68].
It provides two profiling backends (vLLM-0.9.0 [42] and Transformers v4.52.1 [30]) and employs GPT-5’s agent mode [61] to mutate model configuration files,
which has web-search capability to retrieve
relevant code.
In total, HFProbe comprises 8,962 lines of code, including both standalone modules and framework modifications.

Research Questions.
Our experiments aim to evaluate Model2Kernel’s effectiveness
in detecting memory bugs in real-world CUDA kernels
(Section [5.1](#S5.SS1)), its coverage of CUDA memory bugs (Section [5.2](#S5.SS2)), its advancements over existing
techniques (Section [5.2](#S5.SS2)), and the rationale behind
combining dynamic model profiling with CUDA-specific symbolic execution (Section [5.3](#S5.SS3)).

Experimental Settings.
The majority of experiments are conducted on a server
equipped with an Intel(R) Xeon(R) Silver 4110 CPU,
256 GB RAM, and Red Hat Enterprise Linux 9.
We use clang++ 13.0.0 to compile CUDA code with --cuda-gpu-arch=sm_80
to target CUDA 12.1 and -emit-llvm to generate LLVM IR for cuKLEE.

#### 5.1.1 Methodology

As shown in Table [4](#S5.T4), we evaluate Model2Kernel
on models and kernels from three real-world sources.
First, we extract all text-generation models and their associated kernels from vLLM-0.9.0, the latest release at the start of this project, yielding 62 models and 50 kernels, with substantial kernel reuse across models.
Because vLLM omits config.json files, we retrieve them from Hugging Face by querying model IDs specified in vLLM’s tests,
and selecting the config.json from the top-ranked repository for each model.
Second, we gather all Hugging Face models that contain custom CUDA kernels, resulting in 54 models and 117 unique kernels.
Third, we survey recent top-tier AI conference papers from the past two years and identify four [81, 55, 64, 39]
whose artifacts provide both Hugging Face models and custom kernels, contributing four models and six kernels.
In total, our evaluation includes 120 models and 173 kernels, comprising 170,875 lines of Python model code
and 139,951 lines of CUDA code.

We evaluate benchmarks from the first source
using the vLLM backend and the remaining benchmarks using the Transformers backend. For each model,
we attempt configuration mutation only once for any CUDA kernel that
is statically reachable but not triggered by the collected config.json.
For every configuration (both original and mutated),
we test nine combinations of batch sizes $\{1,3,5\}$
and sequence lengths $\{1,7,17\}$,
chosen to keep profiling short while remaining realistic and uncommon.
Each CUDA kernel is analyzed by cuKLEE for up to one hour, following common practice in prior symbolic-execution work [11, 41, 51].

For each bug reported by cuKLEE,
we examine the corresponding CUDA code to
verify whether the reported tensor shapes and input values
indeed trigger the issue.
We further assess whether the shapes and values are semantically valid and
whether any logic in the model or inference framework
would prevent them from reaching the kernel.
To ensure objectivity, each bug is independently reviewed by at least two authors. Because vLLM kernels are shared across models,
we merge vLLM bug reports with the same root cause and kernel line number,
even if triggered by different models. For out-of-bounds accesses resulting from a preceding integer overflow,
we count only the integer overflow.

#### 5.1.2 Experimental Results

As shown in Table [4](#S5.T4),
Model2Kernel detects 353 memory bugs in CUDA kernels, comprising 328 integer
overflows and 25 out-of-bounds accesses. No data races or null-pointer dereferences are identified.
The large number of findings demonstrates
*Model2Kernel’s effectiveness in validating the memory safety of CUDA kernels.*

In addition, Model2Kernel detects bugs across benchmarks from all three sources,
underscoring *its ability to analyze diverse models and kernels*.

Figure: Figure 4: A detected integer overflow bug.

Integer Overflows.
All integer overflows detected in the vLLM and Hugging Face benchmarks occur on int32 values.
Of these, 198 result from multiplying the token count
by the hidden size. In 106 cases, the overflowed value is subsequently
used to index a tensor storing per-token dimensions,
causing out-of-bounds accesses.
Figure [2](#S1.F2) illustrates one instance.
Another 98 cases occur when
computing indices for the $QK^{\top}$ output, where the
maximum index can reach
$\texttt{batch_size}\times\texttt{num_heads}\times\texttt{seq_len}^{2}$ and
exceed the int32 limit. Four additional
overflows arise from multiplying the token count by
1,024 (thread count), and one more from
multiplying the token count by the number of experts.

Figure: Figure 5: An out-of-bounds bug from vLLM.

The remaining three int32 overflows arise from multiplying the token count by the number of output features. One example is the sub-expression
row_offset * OC in line 13 of Figure [4](#S5.F4.fig1).
For Mistral-7B, OC is 28,672 (line 2).
The long expression in line 11 determines row_offset, whose upper bound is M, the number of tokens.
Several components of line 11 are statically known: with OC = 28,672 and N = 128, j_factors1 evaluates to 224 (line 7); local_id is at most 7 (line 10); and threadIdx.x is at most 31 based on the wrapper (line 3).
However, blockIdx_y depends on another complex expression in line 8 that involves blockIdx.x, which itself depends on launch configuration and M. This complex dependency chain makes such overflows extremely difficult to identify manually.
In contrast, Model2Kernel automatically detects that the overflow occurs when the number of input tokens M is larger than 74,896.

The 24 integer overflows identified in the research-paper benchmarks all
arise from the same code fragment, which appears 24 times.
In this
fragment, a 32-bit integer is shifted left by 10 bits and
then cast to a 16-bit integer. When the shifted value exceeds 31, an overflow occurs.
Neither the model code nor the
CUDA kernel imposes any constraint to prevent this value
from exceeding
that limit.

Buffer Overflows.
Nine buffer overflows occur in scenarios where data are partitioned into blocks but the final block is only partially populated; nonetheless, the CUDA kernels access it as if it were fully valid.
The remaining 16 are cases where an input tensor’s content is used
to compute indices
to access another tensor, and the
kernel does not have adequate validation of the results, leading to out-of-bounds accesses.
For them, we further confirm that the framework code permits the
buggy tensor content to pass into the kernel.

False Positives.
Model2Kernel reports nine false positives,
yielding a false discovery rate of 2.49%.
These arise from three sources.
First, four cases stem from HFProbe’s inability to track tensor values across kernels. Because it returns tensors with zero values for kernel binding functions, subsequent kernel bindings cannot track valid value ranges for those tensors,
producing two
integer-overflow and two out-of-bounds false positives.
Second, two false positives involve kernels that index tensors using values loaded from model weights. As HFProbe does not load the actual weights, it cannot accurately capture the indices; manual inspection confirms
that the true weight values cannot trigger errors.
Third, three false positives arise because cuKLEE reports tensor shapes that are infeasible given constraints enforced by vLLM code.
For example, it flags an out-of-bounds error for input 250, since a tensor’s size cannot evenly divide 250, whereas vLLM permits only 128 or 256.

Time and Monetary Cost.
Model2Kernel requires 985.95 total hours to complete its analysis:
972.54 hours for the vLLM benchmarks, 11.23 hours for Hugging Face,
and 12.18 hours for research papers.
Experiments run with multiple parallel processes,
and the reported time reflects their aggregate.
Using GPT’s agent model costs $442.16.
Considering that both the Python and CUDA codebases exceed 100,000 lines,
Model2Kernel incurs moderate time and monetary costs.

More specifically, cuKLEE consumes 902.19 hours,
substantially more than HFProbe (103.66 hours).
HFProbe generates 1,274 distinct model configurations.
Because many vLLM kernels are shared across models,
we merge identical analysis contexts, yielding 8,562 unique contexts for cuKLEE.
Kernel analysis completes within one hour for 7,784 cases
and reaches the limit for 778 cases. All kernels exceeding one-hour limit
contain 600+ lines of CUDA code.

Answer to effectiveness:
Model2Kernel can accurately detect integer overflows and buffer overflows in CUDA kernels used within LLM inference systems.

#### 5.2.1 Methodology

We use the 20 known vLLM bugs analyzed in Section [2.3](#S2.SS3) to evaluate coverage.
Most of these bugs were reported by vLLM users,
and the corresponding model information is not available.
However, the bug reports or developer discussions typically include the kernel in which the bug occurs and the required inputs (e.g., tensor shapes).
Therefore, in this experiment, we evaluate only cuKLEE.
We retain the input fields mandated by the model architecture and treat all other inputs as symbolic when running cuKLEE.

We compare cuKLEE with three static CUDA analysis tools: Honeycomb’s validator [54],
GKLEE [47], and
ESBMC-GPU [65].
These tools cannot run directly on vLLM kernels due to
incompatibilities with modern C++, CUDA, as well as PyTorch and vLLM CUDA libraries (e.g., Tensor). Moreover, GKLEE and ESBMC-GPU require a main() as their entry point,
which vLLM kernels lack.
To enable comparison, we simplify the vLLM kernels
by rewriting modern CUDA/C++ features with legacy constructs,
removing PyTorch and vLLM CUDA dependencies,
and adding a main() function for each kernel that replaces the original wrapper and allocates GPU memory for tensors.
These simplified kernels preserve the root causes of the bugs. Because Honeycomb targets HIP kernels [4], we additionally translate CUDA APIs to HIP equivalents using hipify-perl [3].
We do not compare with other related tools
because they are not free [20, 62]
or their code is not available [14, 46, 48, 35].

#### 5.2.2 Experimental Results

As shown in Table [5](#S5.T5), cuKLEE identifies 15 of the 20
known bugs, including nine integer overflows, five out-of-bounds
accesses, and one NULL-pointer dereference, demonstrating strong
coverage of real memory errors in CUDA kernels.

Figure [5](#S5.F5.fig1) shows an out-of-bounds error.
The wrapper function (omitted for brevity) allocates shared memory to record how threads assign tokens to experts. As shown in line 2,
the first num_experts + 1 entries store the total token count and
the per-expert counts. The remaining entries
form a two-dimensional array storing
how many tokens each thread routes to each expert,
plus one slot
per expert for the expert’s total. Line 5 attempts to
skip this first region so that lines 7–9 operate the second region.
However, it incorrectly uses the number of threads (blockDim.x),
rather than the number of experts, to compute the offset. As marked in line 1,
when the expert count is below 32, the thread count
exceeds it, leading to a buffer overflow in line 8.
cuKLEE correctly reports the buffer overflow at the line,
with threadIdx.x=31 and num_experts=8.

The missed bugs arise for several reasons.
First, one NULL-pointer dereference occurs because
the kernel is launched on a different GPU than the data it accesses,
which is undetectable via static analysis.
Second, one out-of-bounds error is caused by a mismatch between
a tensor’s declared shape and the underlying memory layout;
cuKLEE assumes consistency between these properties and
therefore misses the issue. Third, two bugs exceed the one-hour analysis limit
and remain undetected.
Fourth, cuKLEE lacks support for C++ std map,
causing it to miss one bug that depends on this construct.
For the simplified kernels, cuKLEE still fails to detect the
first bug but successfully identifies the other four.

Honeycomb detects no bugs because
it only checks whether memory accesses stay within one
of four coarse regions (protected, read-only, read-write, and private).
All tested out-of-bounds accesses fall inside the read-write region, so Honeycomb cannot catch them.

GKLEE detects one integer overflow and four out-of-bounds accesses, but misses the remaining bugs for three reasons. First, seven bugs occur only
when threadIdx.x or blockIdx.x exceed 30,
while GKLEE assumes small constant values for both.
Second, GKLEE fully unrolls loops, causing the analysis of seven buggy kernels to hit the one-hour timeout.
Third, GKLEE cannot pinpoint the bug due to the kernel and its data on different GPUs.

ESBMC-GPU identifies one integer overflow and two out-of-bounds accesses. It misses nine, seven, and one bugs respectively for the exact same reasons as GKLEE.

Answer to coverage and advancement:
cuKLEE detects most of the tested known bugs, substantially more than the baselines, demonstrating its strong coverage of real CUDA memory bugs and its advantages over existing techniques.

#### 5.3.2 Experimental Results

The full-featured version of Model2Kernel detects the most
bugs in Figure [6](#S5.F6), demonstrating the value of each component.

Removing HFProbe causes cuKLEE to report 5,527 false positives for two reasons.
First, cuKLEE may infer tensor shapes that are theoretically possible but never occur in reality, leading to incorrect out-of-bounds reports.
For example, in Figure [2](#S1.F2), cuKLEE incorrectly assigns tensor input the shape $(256,256)$ and tensor residual the shape $(8)$
to trigger out-of-bounds access in line 22 of Figure [2](#S1.F2), as the two tensors are accessed with the same index inside the loop.
However, the two tensors always share the same shape in practice,
making such a case infeasible.
Second, cuKLEE may treat tensor shape values or other parameters as having extremely large, unrealistic values (e.g., a hidden size of 2,147,483,640).
Moreover, without model-architecture information,
all tensor shapes become symbolic, forcing cuKLEE to explore far
more possibilities. As a result, it fails to complete the analysis of 23
kernels within one hour, 16
more than when architecture information is provided in Section [5.1](#S5.SS1), and increases the average analysis time per kernel by $2.5X$.

With cuKLEE disabled,
no runtime errors are detected, so this variant reports
nothing. Our experiments use a maximum batch size of 7
and a sequence length of 17 (only 119 tokens in total),
far too few to expose hidden bugs. This shows that Model2Kernel uncovers issues that would otherwise appear only at large production scales.

Without configuration mutation, only 21 of the 50 CUDA kernels are exercised, leading Model2Kernel to miss 32 bugs.

Answer to rationality:
Each component of Model2Kernel plays a distinct and essential role in its overall effectiveness.

## 6 Limitations and Discussion

Model2Kernel currently focuses on Hugging Face models and CUDA kernels with tensor inputs,
which cover a large portion of real-world usage.
However, due to the ecosystem’s diversity and rapid evolution, Model2Kernel does not yet support components such as Triton-based kernels or TensorFlow models. Its core ideas—mutating model configurations to explore diverse execution paths,
modeling dynamic arrays as discrete memory regions, and symbolizing thread IDs—can be generalized to other bug types and CUDA kernels. Extending cuKLEE to NPU instruction sets and NPU kernels is a promising direction for future work.

In Section [4.2](#S4.SS2), we mutate execution configurations to trigger additional CUDA kernels. While this increases coverage, collected contexts still represent only a small fraction of real LLM inference scenarios.
Developing more systematic methods to explore inference frameworks and validate kernels under broader, realistic contexts remains future work.

In our experiments, cuKLEE analyzes each kernel for up to one hour.
For certain kernels (e.g., gptq_marlin_gemm(), moe_wna16_marlin_gemm()),
not all paths are explored, potentially missing
memory bugs. cuKLEE builds on KLEE and inherits
its path exploration strategies, originally
designed for C/C++. Since CUDA kernels may follow
different programming patterns,
optimizing path exploration for CUDA is a key
direction to improve cuKLEE’s effectiveness.

## 7 Related Work

Exploiting CUDA Memory Bugs.
Prior work shows that CUDA memory bugs are highly exploitable [34, 69].
They can enable control-flow hijacking [26, 57], mind-control attacks [63], and side-channel attacks [66, 58, 85],
leading to severe inference degradation or arbitrary code execution.
These findings motivate our systematic analysis of CUDA kernels to detect memory bugs in them.

Static techniques
have been developed for CUDA kernels. ProofWright [14] uses
Vercons to verify kernels against LLM-generated specifications. COVT [50] translates CUDA into C/C++
and then detects integer and buffer overflows.
Honeycomb’s validator [54]
ensures memory accesses remain within predefined coarse-grained regions.
Tong et al. extend Dartagnan with GPU consistency models [75]. Symbolic-execution-based
methods have also been proposed [6, 46, 48, 35, 47, 65].
Overall, these static techniques struggle with dynamically
sized memory buffers, do not support the widely used Tensor library, and cannot handle varied kernel launch configurations.
We evaluate three of them [54, 47, 65] in Section [5.2](#S5.SS2) and find they are limited in usability and less effective than cuKLEE. Commercial static tools also exist [20, 62], but their technical details are unavailable for analysis.

Dynamic Techniques.
NVIDIA provides several mechanisms to enforce GPU memory safety. By default, the GPU MMU reports “illegal memory access”
errors when untracked virtual addresses are accessed [56].
CUDA-MEMCHECK [59] and its successor Compute Sanitizer [60] record metadata for GPU buffers, enabling detection of a broader range of memory errors at the cost of increased runtime overhead.
Researchers have also devoted efforts in this area.
GPUShield [43], GPUArmor [92], cuCatch [73], and LAK [82] build on similar principles as Compute Sanitizer, with the first three emphasizing lower runtime overhead and latter using lock-key metadata
to provide stronger memory safety.
GMOD [27, 25] pads memory buffers and detects overflows by monitoring changes to the padding.
IMT [71] leverages ECC to ensure GPU memory safety.
Race detection tools, including BARRACUDA [28], GRace [88], GMRace [89], and LDetector [49],
track the last-accessing thread for each memory location and identify unsynchronized concurrent accesses.
Despite these advances, these techniques rely on specific inputs to trigger bugs, require instrumentation or hardware support, and many incur large runtime overhead.

## 8 Conclusion

This paper presents Model2Kernel, an automated tool that combines
dynamic model profiling with CUDA-specialized symbolic execution to detect CUDA memory bugs in LLM inference systems.
Model2Kernel identifies more than 300 CUDA memory bugs in popular LLM inference frameworks when they perform inference with real models, demonstrating its practical effectiveness. Future work can further improve
the efficiency of symbolic execution for CUDA kernels
and extend Model2Kernel to support NPU kernels.
