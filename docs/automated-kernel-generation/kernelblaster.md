## Background

KernelBlaster is motivated by a practical failure mode in GPU optimization: hardware and workloads evolve faster than manually tuned kernels. An optimization that worked for one generation or one workload can become suboptimal once the target GPU architecture or model execution pattern changes. The paper frames this as a continual adaptation problem rather than a one-off code generation task.

The central claim is that existing agentic CUDA workflows do not accumulate enough reusable knowledge across tasks. They explore locally, improve a kernel, and then effectively forget what they learned. KernelBlaster addresses this by introducing a persistent memory structure so that optimization experience from one task can inform later tasks and later hardware targets.

**Key Takeaways**

- KernelBlaster casts CUDA optimization as a memory-augmented in-context reinforcement learning problem instead of pure prompting or static search.
- The system stores optimization knowledge in a Persistent CUDA Knowledge Base that is updated with profiling-driven experience.
- Against PyTorch, the framework reports geometric mean speedups of 1.43x, 2.50x, and 1.50x on KernelBench Levels 1, 2, and 3 respectively.

## Methodology

KernelBlaster uses a Memory-Augmented In-Context Reinforcement Learning (MAIC-RL) framework. Instead of updating model weights through standard RL training, the system treats the prompt context itself as the mutable policy state. That policy state is stored in a Persistent CUDA Knowledge Base containing optimization strategies, associated performance states, and their expected gains.

The optimization loop works by profiling generated kernels, extracting a performance signature, matching the current kernel to known performance states, retrieving candidate optimizations from memory, and then applying a weighted search over those candidates. After validation and profiling, the observed performance is written back to the Knowledge Base. This creates a continual cross-task improvement loop in which later optimization attempts benefit from prior search traces.

### System Overview

| Component | Input | Output | Role |
| --- | --- | --- | --- |
| State Extractor | Runtime profiling information and code | Performance state signature | Converts low-level execution behavior into retrievable textual state |
| State Selector | Current kernel state and Knowledge Base | Matching prior states and candidate optimizations | Reuses relevant experience from earlier tasks |
| Optimization Selector | Candidate optimizations and expected gains | Top-k optimization actions | Performs weighted exploration over promising strategies |
| Lowering Agent | Selected optimization and source program | New CUDA implementation | Applies and validates the optimization |
| Policy Evaluation | Generated code plus observed performance | Updated memory entries and textual gradient signal | Measures discrepancy between expected and actual performance |
| Parameter Update | Knowledge Base plus policy gap analysis | Refined prompt policy | Revises the persistent optimization policy without changing model weights |

### Classical RL vs. KernelBlaster In-Context RL

| Classical RL Concept | KernelBlaster Analogue |
| --- | --- |
| Policy `pi_theta(a_t | s_t)` | LLM agent conditioned on a mutable context document |
| State `s_t` | Unoptimized CUDA code before a transformation |
| Action `a_t` | Optimization generated by the LLM |
| Next State `s_{t+1}` | Optimized code after applying the action |
| Reward | Measured discrepancy between expected and actual performance from execution |
| Parameters `theta` | Persistent CUDA Knowledge Base and prompt context |

### Key Design Choices

- Memory is persistent across tasks, which enables long-horizon reuse rather than isolated single-task search.
- Policy updates are textual: one agent analyzes performance discrepancy and another rewrites the optimization context accordingly.
- Profiling feedback is dense and low-level, so the update signal contains more than a single scalar speedup.
- The framework explicitly targets cross-task and cross-generation adaptation rather than only optimizing a single benchmark kernel.

## Experiment

### Experimental Setup

| Item | Value |
| --- | --- |
| Baselines | PyTorch eager / `torch.compile`, AI CUDA Engineer, IREE compiler |
| Hardware | NVIDIA A6000, A100, H100, L40S |
| Dataset | KernelBench Level 1, Level 2, and subset of Level 3 |
| Main Agent Models | GPT-4.1 and GPT-5.0 |
| Iteration Budget | 10 iterations, 10 rollout steps per iteration |
| Validation | GPU execution against PyTorch with randomized seeds |
| Primary Metrics | Valid rate, average speedup, geometric mean speedup, `% > 1x` |

### Headline Results

| Platform / Level | System | Valid Rate | GeoMean Speedup | `% > 1x` |
| --- | --- | --- | --- | --- |
| L40S / Level 1 | IREE | 85% | 0.268x | 21.18% |
| L40S / Level 1 | AI CUDA Engineer | 82% | 1.101x | 74.39% |
| L40S / Level 1 | KernelBlaster | 93% | 1.080x | 59.72% |
| L40S / Level 2 | IREE | 83% | 0.279x | 16.87% |
| L40S / Level 2 | AI CUDA Engineer | 83% | 1.695x | 79.52% |
| L40S / Level 2 | KernelBlaster | 95% | 2.214x | 72.60% |
| H100 / Level 1 | AI CUDA Engineer | 82% | 1.025x | 64.20% |
| H100 / Level 1 | KernelBlaster | 86% | 1.497x | 70.37% |
| H100 / Level 2 | AI CUDA Engineer | 82% | 1.214x | 61.33% |
| H100 / Level 2 | KernelBlaster | 81% | 2.592x | 84.85% |
| Level 3 | KernelBlaster | 67% | 1.502x (L40S) / 1.110x (H100) | 75.0% |

The strongest results appear on KernelBench Level 2, where KernelBlaster reports large advantages over both AI CUDA Engineer and IREE. On H100 Level 2, the geometric mean speedup reaches 2.592x with 84.85% of kernels exceeding the baseline. The framework also scales to Level 3 full-model settings, where it still reports positive gains even though the optimization target is much larger than a single isolated kernel.

### Comparison Summary

| Comparison Axis | KernelBlaster Result |
| --- | --- |
| Against PyTorch baseline | 1.43x / 2.50x / 1.50x geometric mean speedup on KernelBench Levels 1 / 2 / 3 |
| Against AI CUDA Engineer | Stronger Level 2 gains and better performance on harder optimization settings |
| Against IREE | Higher speedups across the reported CUDA-focused comparisons |
| Against full-model workloads | Still positive on Level 3, including SqueezeNet Fire Module example |

### Representative Optimizations

| Case | Reported Gain | Main Optimization Theme |
| --- | --- | --- |
| KernelBench Level 2 Q18 | 20.17x over PyTorch | Algebraic simplification plus kernel fusion and warp-shuffle reductions |
| Tensor-core GEMM case | Hardware-aware split-K + WMMA + FP16/FP32 accumulation | Tensor-core utilization and structured epilogue design |
| SqueezeNet Fire Module | 1.2x over PyTorch | Multi-kernel fusion, read-only caching, and cooperative reduction |

These case studies reinforce the paper's main thesis: the framework is not only trying random rewrites. It accumulates reusable optimization patterns such as algebraic elimination, tensor-core mapping, split-K parallelism, and fusion strategies, then re-applies them when similar states appear again.

## Limitation

KernelBlaster is ambitious, but it also introduces a more complex optimization stack than simpler prompting or search baselines. Its reported gains rely on persistent memory, profiling-rich feedback, and several coordinated agents.

| Limitation | Why It Matters |
| --- | --- |
| Converted source metadata is incomplete | The paper conversion did not preserve author metadata cleanly, which makes exact attribution brittle in downstream tooling |
| The system is operationally heavy | Persistent memory, replay buffers, profiling, and multi-agent updates increase engineering and runtime overhead |
| Results vary by benchmark level and hardware | Gains are strongest on some levels and devices, which suggests uneven robustness across tasks |
| Level 3 improvements are smaller | Full-model optimization remains harder than isolated kernel optimization |
| Reinforcement is still in-context | The framework avoids expensive retraining, but it also depends on the quality and maintenance of the textual memory policy |
