## Background

MaxCode studies optimization tasks where a language model starts from correct but slow code and must iteratively produce faster variants. This is harder than ordinary code generation because success depends on both functional correctness and hardware-sensitive performance. Raw execution feedback such as compile errors, test failures, or a single speedup number is often too weak to explain why a candidate is slow or what transformation should come next.

The key reframing is to treat code optimization as a max-reward reinforcement learning problem. The objective is not cumulative reward across all intermediate steps, but the best performance found anywhere along the search trajectory. That viewpoint matches kernel and systems optimization more naturally: many intermediate edits are only useful if they eventually lead to one high-quality candidate.

**Key Takeaways**

- MaxCode extends iterative code optimization with a state that includes execution feedback, natural-language critique, and the best reward seen so far.
- The framework is modular: existing search methods such as Effi-Learner and CUDA-LLM can be rewritten under the same max-reward inference operator.
- A learned reward-to-go model is explored as an additional search guide, but its gains are mixed and sensitive to distribution shift.

## Methodology

MaxCode defines an extended MDP where each state is `s_t = (x_0, x_t, e_t, c_t)`: the original problem and seed implementation, the current candidate code, executor feedback, and a critique generated by a separate LLM. The system also maintains an auxiliary variable `u_t` for the best discounted reward found so far. This makes the search policy condition on both the current candidate and historical best performance, which standard iterative prompting does not encode explicitly.

The framework then approximates a max-reward inference operator over a fixed code-generation policy. In practice, this means sampling candidate rewrites, executing them, attaching critique, updating `u_t`, and selecting which branch to continue. MaxCode instantiates this idea by reformulating Effi-Learner and CUDA-LLM. It additionally trains a categorical reward-to-go model that predicts the best future reward achievable from a partial search trajectory and uses that prediction to rerank candidates before expensive execution.

### System Overview

| Component | Input | Output | Role |
| --- | --- | --- | --- |
| Executor `EX` | Candidate code and test cases | Correctness signal, performance signal, diagnostic feedback | Provides the grounded reward used for search |
| Critique Model `pi_c` | Candidate code plus execution feedback | Natural-language diagnosis and refinement hints | Converts low-level feedback into actionable search context |
| Generator Policy `pi_theta` | State `(x_0, x_t, e_t, c_t)` and best reward `u_t` | New code revision | Proposes the next optimization candidate |
| Max-Reward State Tracker | Sequence of executed candidates | Best discounted reward `u_t` | Preserves the max-reward objective across steps |
| Reward-to-Go Model `V~_phi` | Partial trajectory prefix | Estimated future max reward category | Filters or reranks promising candidates before execution |

### Reformulated Search Methods

| Method | Original Behavior | MaxCode Reformulation |
| --- | --- | --- |
| Effi-Learner | Two-round refinement using execution feedback | Adds critique to the intermediate state; `u_t` is implicit because the horizon is short |
| CUDA-LLM | Multi-candidate beam-style refinement with best-candidate continuation | Adds critique to every state and injects best-so-far reward into candidate generation |
| Reward-Guided Search | Not present in the baseline methods | Uses a learned categorical reward model to prioritize branches with higher future upside |

### Key Design Choices

- The reward objective is the best achieved speedup on a trajectory, not the sum of intermediate improvements.
- Critique is part of the observation space rather than a post-hoc explanation layer.
- Continuous speedups are bucketed into 5 reward categories, with dataset-specific thresholds for KernelBench level 1, KernelBench level 2, and PIE.
- The reward model is trained from rollout prefixes collected by MaxCode search, using Qwen2.5-7B-Instruct with LoRA as a lightweight generative value estimator.

## Experiment

### Experimental Setup

| Item | Value |
| --- | --- |
| Benchmarks | KernelBench (CUDA) and PIE (C++) |
| KernelBench Scope | Level 1 and Level 2, 100 problems each |
| PIE Scope | 68 sampled test problems |
| Generator / Critic LLM | Claude-3.7-Sonnet |
| Temperature | 0.6 for code and critique generation |
| Effi-Learner Budget | Single-path refinement, depth = 2 |
| CUDA-LLM Budget | Depth = 8, `K = 8` candidates |
| Reward Model | Qwen2.5-7B-Instruct + LoRA rank 8 |
| Metrics | Correctness, Fast1, median max speedup, average rank of max speedup |

### Headline Results

| Method | KernelBench L1 | KernelBench L2 | PIE |
| --- | --- | --- | --- |
| Best@64 | Rank 2.85, Median 1.00x | Rank 2.15, Median 1.02x | Rank 2.29, Median 1.32x |
| Effi-Learner | Rank 3.02, Median 1.00x | Rank 2.98, Median 1.00x | Rank 3.72, Median 1.00x |
| Effi-Learner + MaxCode | Rank 2.98, Median 1.00x | Rank 2.95, Median 1.00x | Rank 3.55, Median 1.03x |
| CUDA-LLM | Rank 1.54, Median 2.49x | Rank 1.64, Median 1.45x | Rank 2.05, Median 1.42x |
| CUDA-LLM + MaxCode | Rank 1.43, Median 3.17x | Rank 1.51, Median 1.61x | Rank 1.74, Median 1.74x |

The strongest result comes from combining MaxCode with CUDA-LLM. Relative to vanilla CUDA-LLM, the paper reports median speedup gains of 27.3% on KernelBench level 1, 11.0% on level 2, and 22.5% on PIE. These gains align with the overall claim that critique plus best-so-far reward makes the search more sample-efficient under the same execution budget.

### Reward-Guided Search

| Setting | KernelBench L1 | KernelBench L2 | PIE |
| --- | --- | --- | --- |
| MaxCode | Rank 1.40, Median 3.24x | Rank 1.57, Median 1.22x | Rank 1.55, Median 1.72x |
| MaxCode + Reward | Rank 1.53, Median 2.44x | Rank 1.33, Median 1.24x | Rank 1.43, Median 1.62x |

The learned reward model helps some settings but does not produce a clean win. It improves ranking on KernelBench level 2 and PIE, slightly improves median speedup on level 2, but degrades median speedup on KernelBench level 1 and PIE. This makes the reward model more of an exploratory direction than a solved component.

### Ablation Findings

- Trajectory history plus critique is the most consistently useful prompt augmentation.
- Adding only one auxiliary signal often yields limited gains and can slightly hurt performance.
- Under the same search depth, MaxCode reaches stronger median speedup earlier than vanilla CUDA-LLM, indicating better test-time scaling.

## Limitation

The paper explicitly identifies reward-model accuracy and trajectory distribution shift as the main reasons reward-guided search remains unstable. The training rollouts use a different search dynamic from the guided inference procedure, so the learned value estimator is asked to generalize out of distribution.

| Limitation | Why It Matters |
| --- | --- |
| Reward model is inconsistent | It underperforms plain MaxCode on KernelBench level 1 and lowers median speedup on PIE, so learned guidance is not yet reliable |
| Evaluation scope is partial | KernelBench experiments only cover levels 1 and 2, and PIE uses a 68-problem subset rather than the full benchmark |
| Search remains execution-bound | Every branch still requires compilation and runtime evaluation, which constrains deeper exploration |
| Critique quality is not isolated directly | The paper shows that critique helps in combination with trajectory information, but it does not separately benchmark critique fidelity |
